# routing — the hard rules in full

SKILL.md carries each rule as the one line that decides a dispatch. This file is the full rule:
one line per rule, its reason, and the slug of the vault ruling or lesson that holds its history
(`fleet/rulings/<slug>.md`, `fleet/lessons/`, or `projects/<p>/decisions/`). Where a script does the
work, the rule names the script; its `--help` is the procedure.

# Routing — who does the work

The orchestrator's job is dispatch. Doing work inline that a persona or skill owns is a routing
failure **even if the output is correct** — it starves the fleet, bypasses skill discipline, and makes
usage unauditable. Skills do not auto-fire; the always-on identity gate in `rules/routing.mdc` is what
every turn sees (`2026-08-01-routing-identity-gate`).

## Hard rules (non-negotiable)

1. **Research never stays home.** Any lookup, comparison, market/competitor question, "what's the best X", "cutting edge", or sourced question about the live world → dispatch **Researcher**, whose method is `research-synthesis` (WebSearch + WebFetch; never training memory). Never answer research from memory; never substitute Explore/general-purpose for live-world research. **Question shape, not only topic:** "is X good for Y", "compare", "should we use" goes to the Researcher; the parent may give at most a one-line holding answer labelled unverified (`session9-lessons-2026-10-04`).
2. **Figma reads go through `capture-figma` on the dispatched persona.** A pasted figma.com URL, "fresh sync", "the figma version", "discrepancies with figma", or any need for instance `componentProperties`, tokens/variables/variants/component names/copy from a design file → brief names file+node; the **doer** loads `capture-figma` and reads via REST (`scripts/figma-node.mjs` / `scripts/figma-capture.mjs`, or banked capture JSON). Parent capture-figma **locates** only (file key, node id, frame; MCP ping the tab is fine). A brief that pastes the finished prop table is a steer — name the node; live props win. Figma screenshots in chat are context, never a substitute.
   - **Figma MCP tools reach only the generic `claude` agent type** — `ux-designer` lanes cannot see the deferred `use_figma` tools; a `claude`-type lane with an explicit ToolSearch `select:` list can. **In a cloud session no subagent gets them**: brief the REST route (`capture-figma/references/LANES-AND-TOOLS.md` § No-export lanes); the parent alone holds the MCP and `use_figma` writes.
   - The annotation setter re-escapes `&` on every whole-array write: write every entry from decoded text in one shot and re-read. A `use_figma` annotation lands on the nearest instance of the text you walk from (`.ActionButtonTitle`): walk up to the outermost instance whose name has no `.` prefix first.
   - **A `use_figma` variable add or rename is never a technical call**: it needs a settled `handoff-css resolve` report first — `dispatch-brief/references/FIGMA-VARIABLES.md`; `figma-variable-gate` refuses it without one (DISC-347, `2026-11-21-s105-parent-lessons`).
3. **Built-vs-design checks go through `audit-build`** ("the blocks are off", "doesn't match figma", post-port verification) — dispatched to UX Designer.
4. **Live-site references go through `capture-website`** ("look at this site", "like pentagram does", any external URL offered as a reference).
5. **Explore/Plan are reconnaissance only.** The orchestrator may use built-in Explore/Plan for its own codebase orientation before writing a brief — never as a substitute for work a persona owns, and never for anything the operator asked to be researched, designed, built, reviewed, or released.
6. **The fleet merges and ships; the orchestrator merges only its own notes-only vault PRs** (`2026-07-26-fleet-merges-and-ships`). **The reviewer informs; the gate-run tail and the parent decide.** Reviewer returns severity-ranked findings (red / amber / note), never a bare merge verdict and never a write. **Merge condition: deterministic gates green + no red finding open** — the parent remits, loading **`present-for-review`** first when a live product exists, then dispatching merge execution to Engineer (mid-stream integration) or Release Ops (release-gated). **Engineer complete is not merged.** After engineer lands, solicit review before the operator hears "fixed".
   - **Every merge has a reviewer verdict first** — a one-line test-only PR gets a LIGHT pass; "small, gates green" is not a review record (`2026-10-09-every-merge-reviewed`; notes-only vault PRs (jhd-vault, markdown records, indexes, queue/backlog rows only; scripts, hooks, CI, settings get a reviewer) are the orchestrator's own merge, `2026-10-18-orchestrator-merges-own-vault-notes`). Checked: `hooks/bin/merge-review-gate.mjs` refuses `mcp__github__merge_pull_request` unless it pins `expectedHeadSha` and a reviewer verdict on that head (shape in `agents/reviewer.md` § Verdict) saying `merge: yes` was read in the session; a MrJarrad/jhd-vault PR passes only when it is shown notes-only: by `node <plugin>/hooks/scripts/vault-pr-files.mjs --vault <vault> --pr <n>` (names only, bound to the head; use this; `<plugin>` as an absolute path, the one the gate's refusal prints) or by `get_files` reads; the gate fails closed. `merge-after-review.mjs` refuses the same (`2026-10-18-helper-waits-for-go`).
   - **Resume pulls main first:** `git fetch origin main`, cockpit and handover from `origin/main`, every "running" lane re-checked against live PR/branch state before any dispatch (`resume-reads-vault-main-first-2026-10-10`).
   - **One review per change; LIGHT is the standing tier** — see `agents/reviewer.md` for the tier and round-cap law.
   - **A design-system merge that changes an API the portfolio uses is followed, in the same session, by the portfolio's pin bump**, because a DS main ahead of the pin breaks every portfolio lane's setup (`2026-11-12-s84-parent-lessons`). DO: queue the pin-bump lane before reporting the DS merge done. DON'T: report the DS merge done while the portfolio pin still points at the old commit.
7. **Grill before dispatch.** Non-trivial build/design: if the decision frontier is not empty, load `grilling` and lock the tree (experience questions, recommended answers) before `Agent`. Cannot write ACs without inventing requirements → grill, not dispatch. Explicit operator skip ("just build it") is the only bypass. Locked decisions go verbatim into every brief.
8. **Baton — parent-only `Agent`.** **Only the orchestrator `Agent`-dispatches.** When the handoff table names the next owner, the **parent** `Agent`-dispatches them on the system completion notification — do not wait for the operator to "notice." Default `run_in_background`; **end the turn** after dispatch — do not AwaitShell/poll the specialist. Specialists are doers (`doer-rules.md` § You are the doer) — they land, name the next owner in evidence, and stop. Parent silence **after the completion ping** is a routing failure. Waiting **inside** the dispatch turn is also a routing failure. Parent is **not a waiting room** (still owns grilling, operator voice, every `Agent` dispatch, merge remittance when the merge condition is met).
9. **Dispatch surface — operator's rule: "if a task can be done in cloud, it is."** Every dispatched agent is a doer — build, fix, verify, triage, review, audit, research alike; the cloud default covers all of them, and the only test is capability, never lane taxonomy, because a dropped local doer dies mid-lane while a dropped main session resumes (`2026-10-03-cloud-by-default`).
   - **Local is justified by exactly three needs**, named in one clause in the brief: (a) **verifying the deployed surface** or presenting it for review (cloud egress 403s `*.workers.dev`); (b) **machine-bound stacks** — `:4411` capture listener, Capture.app helper, figma-daemon, interactive-auth MCPs; (c) **this machine's own state**. A read-only task (research, reading files, a search) needs none of the three, so it goes to cloud too: an `Agent` call from the parent runs local. A `local —` brief says which, on one line: `Local because: (a) …`, `(b) …` or `(c) …`; `agent-dispatch-gate` refuses a local dispatch without it.
   - **A cloud capability gap that is not machine-bound is a setup defect to close**, never a reason to route to the Mac queue. When a cloud action is refused, name which layer refused it (Claude's permission check, GitHub access, or network policy) and give the operator the one-time setting that closes it.
   - **A Mac job carries only the Mac-bound step**: split a release into cloud steps (gate, push) and a Mac step (plugin install), and the brief names why each step is machine-bound. A Mac job that reads the vault pulls it first. Cloud pushes branches but not tags: release tags go via a Mac job until the proxy allows them.
   - **Queuing a Mac job merges the vault branch to main in the same action** — the runner claims only from main; the job's first step names the vault sha it expects (`vault-write` § Banked means on vault main; `session10-codify-candidates-2026-10-05`). The notes-only PR that files the job is the parent's own merge, that turn. DO: file the job, merge its PR, then report it queued. DON'T: leave it for wrap.
   - **A Mac job cannot open an Access-gated preview** — `*.workers.dev` previews 302 to Cloudflare Access, and only the cloud proxy injects credentials. A Mac GPU measurement on a preview needs an Access service token in the Mac's environment (never the vault) or a local build; until one exists, ask the operator for the one-line device check.
   - **A round ends at its merge** (`merge-each-approved-round-2026-10-06`): one open change per approved round, merged as soon as it is approved and green. Stacking a new round on an unmerged branch is malformed; a lane's done-when is the merge of that round.
   - **Egress-gap scope:** the `*.workers.dev` gap blocks only the check of the **deployed** surface. A doer slice verifying its own build on its own port (`doer-rules.md` § Ports) is **not** machine-bound. "Faster", "interactive", or "read-only" is not a clause either (`2026-08-30-egress-gap-scope`).
   - **The surface is chosen when a lane opens, not per task** — same-domain follow-ups resume the standing specialist on its surface; never bounce a domain between local and cloud mid-stream, because context is the asset. **Outgrown/mis-surfaced lane = explicit handoff:** wrap the lane's evidence into a fresh brief on the right surface and re-dispatch — a deliberate handoff with a named context cost, not a retroactive routing failure.
   - **Overlay gate:** cloud dispatch requires the target repo to already carry committed discipline overlays — cloud doers get only what the repo commits. No overlays means overlay refresh (`plugin-update-syncs-everywhere`) comes first; a local dispatch on an overlay-less repo is a named fallback in the brief, never the default reach.
   - **Visible on every dispatch:** the `Agent` `description` leads with the surface — `cloud — persona (model): task` / `local — persona (model): task`; the mechanic lives in `dispatch-brief`'s "Persona + model" section.
10. **`review-the-lock-not-the-slice`.** **First failure point (parent brief):** the locked table is the spec — **the brief must copy it whole.** One AC per locked row; a slice AC set against a whole-surface lock is **malformed — do not `Agent`**. **Work batches ≠ spec width** — caps must not drop locked rows (see `dispatch-brief`). **Paired briefs:** engineer and reviewer briefs share the **same current locked table** (never a reviewer on an earlier narrower table), and the reviewer brief names the lock's **live path** so the reviewer re-reads it — a drifted spec is a **red finding**. **Noted without failing is not a clear review.** The engineer covers every row (or operator-deferred); do **not** solicit review until every locked row is claimed or deferred. Spec incomplete → **red**. Operator widens lock mid-flight → parent **retargets** standing engineer; an in-flight review of the old slice is **not** protected — do **not** answer with *Review is already running on that slice. No second pass.*
11. **Dispatch on the completion notification only.** Harness resume/reconnect prompts after a background specialist are noise — **not leftover**. Parent `Agent`-dispatches the next owner on the **completion notification**; re-sending or re-polling can **double-dispatch**. Never assign "resume the agent" or "send a message to unstick" as operator homework, and never revert baton to a blocking in-turn dispatch to dodge notification handling.
12. **"pause"/"resume" load `pause-resume`, not `wrap`.** "pause", "I need to pause", "wind down", "stop for now", "let's stop here" → no new dispatches, stop running agents at their next safe point, bank a one-screen snapshot, confirm in one line. "resume", "pick up where we left off", "carry on from the snapshot" → read the snapshot, re-dispatch each interrupted lane as a fresh continuation. Pause is not `wrap`.
13. **The full suite/build runs once per PR in a cloud gate-run lane (no GitHub Actions on private repos), its tail posted on the PR — never inside each lane.** A lane's own gates are only the touched ones its size class names (`doer-rules.md` § Size class). The parent runs `lane-sweep.mjs` on every completion notification, and for a landed or stopped lane also `lane-sweep.mjs --clean-artifacts <worktree>...`, which removes that worktree's `node_modules` and `.next` and refuses a root clone. When a lane's PR merges the parent removes its worktree in the same step (`git worktree remove <path>`), because finished worktrees fill the disk (`2026-11-10-s76-parent-lessons`). Before every heavy dispatch the parent reads `df` as well as load: `cloud-dispatch` § Capacity before dispatch. DO: remove the worktree as the merge lands, then read `df`. DON'T: leave finished worktrees for the wrap. A full suite over the Bash tool's foreground timeout is its own gate-run lane, never run from the parent shell (`doer-rules.md` § Repo and safety), and it posts its tail on the PR (`doer-rules.md` § Gate-run tail). A lane stops only its own pids.
14. **Never relay a backlog or queue status unchecked** (ruling `lists-never-stale`). Before the parent tells the operator what is open, in flight or done, it runs `hooks/scripts/list-drift-check.mjs --vault <root> --repo <path>...` (or checks merged PRs and lock rows by hand). A row is judged against the default branch of its own project's repo (a bare `#n` never resolves against another project's repo); a PR the check cannot resolve is `unknown`, never done. `lane-end.mjs` flips the row in the lane's own commit; `wrap` runs the check before the report. **An ask that cites rows is checked first**: `row-add.mjs --to queue` refuses a row naming its project's IDs unless each is open and `list-drift-check.mjs` ran in the last 15 minutes. DO: run the check, then add "HB-196 or HB-197?". DON'T: copy row IDs from the handover into a new ask.
15. **Heavy lanes are capped per container**, because co-scheduled suites, builds and browsers time out and fail suites that pass alone (`2026-10-15-step-failures-audit`). A heavy step (full suite, build, headless browser) counts one; `nproc / 2` is a **ceiling on all heavy lanes together**, not a quota. Inside it: never two full suites at once (`doer-rules.md` § Repo and safety) and one browser repro at a time, no parallel Chromium (`skills/dispatch-brief/references/HOUSE-RULES.md`). Before dispatching a lane whose brief names a heavy step the parent runs `cloud-dispatch` § Capacity before dispatch (disk, load, heavy count); over it, the lane goes to a child cloud session. Lighter lanes (read, write, review) are uncapped. A doer under load runs touched-file tests and leaves the full suite to the gate-run lane.
16. **Lanes sharing a repo** (`preview-builds-and-stale-heads-2026-10-14`): the parent states the live head (`git ls-remote origin <branch>`) in every go message when lanes share a branch; each lane `git fetch`es and rebases before each push, never force. The parent serialises `preview/*` pushes per repo: a lane's brief says when it may push, and a ready lane asks the parent rather than pushing, because concurrent preview builds fail. When a push stops being in flight is defined once, in `present-for-review/references/PREVIEW-PROBE.md` item 6.
17. **Finish before opening** (ruling `2026-10-15-finish-before-opening`), because the limit is the operator's looks, rate-limited preview builds and branch drift, not workers.
   (a) **Cap:** at most 3 look-lanes (try-outs waiting on or heading to the operator's eyes) open per session. A new look topic beyond that is a backlog row (`row-add.mjs`, his words verbatim) unless he says "now". Work that needs no look is not counted; rule 15 still bounds it.
   (b) **Finish line:** after his yes a try-out goes review, gate, merge, or is explicitly parked or dropped, before its slot takes a new look topic.
   (c) **No mid-build piling:** a new ask about a lane that is already building queues for that lane's next round unless tiny (one value or word), and the queued asks print under `## Build in Progress` (`routing` OPERATOR-REPLIES.md).
   Checked: (a) `session-resume.mjs` counts Next-block lanes marked `look: yes` that are still open and warns at 3 or more (`wrap/references/SECTIONS.md` writes the key). Inside a live session the count is the parent's, since no hook sees which lanes are look-judged. (b) and (c) are judgment.
18. **A fix round changes only what the operator named** (`2026-10-15-s25-fix-round-scope`, DISC-169). The round-2 brief and the doer's read-back each carry a `Stays the same` list (every behaviour, value and look the operator did not name); the round changes the named thing and nothing on that list. On a look lane, swapping the mechanism (how the effect is made, not a value inside it) is a new try-out: it waits for the operator's yes first. Checked: judgment; `BRIEF-CRAFT` item 18 and `agents/engineer.md` carry the clauses.
19. **Helper sessions are archived once their lane lands** (`2026-10-15-archive-helpers-on-landing`, DISC-175). A helper is a `create_session` child; the whole recipe (repos, title and tags, model, read-back and go, the return, the sweep, the archive) is `cloud-dispatch/references/HELPER-SESSIONS.md` — read it before the first `create_session`.
   - **At lane end**, after its result is banked, the parent archives it in that same turn: `lane-end --helper <helper id>,<reviewer id>` prints the ordered calls (`get_session`, `archive-prep.mjs`, `archive_session`), so nothing waits for wrap (DISC-325). When the next round of a lane starts, the superseded round's helper is archived then. A helper whose result is not yet banked is never archived.
   - **The helper sweep runs at session start and at wrap** (DISC-211, DISC-212). **At wrap** save `list_sessions` (every page) to files and run `node <plugin>/hooks/scripts/helper-sweep.mjs --self <own id> --sessions <file>… --keep <ids> --merged <ids> --landed <session-dir>/landed-helpers`; wrap writes the Keep and Surface ids, and its own id, on the cockpit wrap block's `Helpers:` line. **At session start** call `get_session` only on the ids in that `Helpers:` line, save each result, and run the same sweep with one `--sessions` per file; the start sweep never pages `list_sessions` (DISC-224). Call `archive_session` on each archive row; the surface list is taken over or reported in the status; a refused archive is one line in the status, never dropped.
   - **The helper ledger is the sweep, and no helper is archived unaccounted for** (DISC-335): at session start and at wrap run `node <plugin>/hooks/scripts/helper-ledger.mjs --self <own id> --sessions <file>… --landed <session-dir>/landed-helpers --vault <vault>` (every `list_sessions` page, no parent filter); its header defines Landed, `## Not landed`, Unknown, `--accept` and `--waiting`; a `## Not landed` helper is named in the status, never archived. The `Pages:` line must say the list is complete before any Archive row is acted on. DO: run the ledger, archive its Archive rows, name its Not landed rows. DON'T: archive a helper from a list you built by hand.
   - **Rule 1: a helper whose work has landed ends archived, with no sidebar step for the operator** (DISC-291). The sweep archives a completed helper under a live parent once it is landed (`--merged`, `--landed`) or has been quiet past 12 hours. It never archives one with an open PR (`--keep`: archiving closes the draft) or one waiting on an operator answer recorded in the queue (`--waiting <ids>`); under a wrapped parent those are Re-point rows, not Archive rows. The Stop hook holds the turn (up to 3 times) until every Archive row has an `archive_session` call after the sweep.
   - **Rule 2: a helper still holding open work when its parent wraps is adopted by the next parent** (DISC-291). Adopt = re-point, track (wrap writes the sweep's `Helpers:` line of ids to the cockpit, plus its own id; a count, "orphans" or "the operator's sidebar" is never a substitute for ids, and the Stop hook holds a wrap whose cockpit write lacks it), archive later. At session start run `helper-sweep.mjs --cockpit <cockpit.md>` for the ids on the last five `Helpers:` lines (it prints ids; the sweep is the call with `--sessions`) and `get_session` each. The Stop hook cannot see a cockpit written by a script from a file.
   - **At session start the parent sends each Re-point row its message**: the sweep's `## Re-point` list carries one `send_message` text per helper whose parent wrapped, naming the new parent's id; send it once, that turn. DO: send the row's message as printed. DON'T: wait for the helper to write to the old parent and re-point it by hand.
   - **A Re-point or any parent-id message carries the parent's own session id read from `get_session` (no id) and pasted, never retyped from the Claude-Session footer.**
   - **Both are checked and fed by script** (DISC-268): the Stop hook holds the turn (up to 3 times) until every Re-point row has a `send_message` after the sweep; `lane-end --helper <session id>` records a landed helper in `<session-dir>/landed-helpers` for `helper-sweep.mjs --landed`.
   - **A parent session is never archived**: a helper is a session with a parent and a title starting "Helper ·"; every other session is a parent and is never passed to `archive_session`. **Hooks enforce it** (DISC-262): `hooks/bin/archive-guard.mjs` denies `archive_session` unless this session's transcript showed that id with a "Helper ·" title and a parent and an open-PR lookup (`HELPER-SESSIONS` § 4) shows none; `hooks/bin/helper-sweep-stop.mjs` blocks an orchestrator session's Stop once per phase until `helper-sweep.mjs` has run. DO: `get_session` the helper first, then archive. DON'T: archive from memory of an id.
   - **A helper starts without a go** (`2026-10-18-helper-waits-for-go`). Every `create_session` prompt opens with "This message is your task — run it now.", then the parent's session id and "start now, no go needed", then the step "First run: mkdir -p ~/.claude && echo <parent id> > ~/.claude/helper-session". The parent checks each new helper with `get_session` within 5 minutes of dispatch and on every wake, and answers a blocked helper the same turn.
   - **A helper's return reaches the parent** (DISC-216). Every `create_session` brief closes with "Send the full return to the parent with send_message (session_id "@parent")." The Stop hook `parent-return-stop.mjs` holds a helper (marked by `~/.claude/helper-session`; no env var marks one, `CLAUDE_CODE_CHILD_SESSION=1` is set in the orchestrator too) once when its turn ends with a return and no `send_message`. The parent arms one `send_later` sweep about 50 minutes out per `create_session` dispatch as the backstop, and deletes it when the return arrives.
   **DO:** prompt opens "This message is your task — run it now. Brief from your parent (session session_01…); start now, no go needed. First run: mkdir -p ~/.claude && echo session_01… > ~/.claude/helper-session", closes with the send_message line; one `send_later` armed; `get_session` 5 minutes later.
   **DON'T:** dispatch the helper and next look at it when the operator asks "how are we looking?".
20. **Redirect a running lane on one channel** (`2026-10-08-redirect-a-running-lane-on-one-channel`): a `SendMessage` redirect resumes that agent even after it has returned; until its next hand-back arrives the work is in flight there, so never dispatch a second lane for it meanwhile. To move the redirect to a fresh agent, `TaskStop` the old one first and say so in the new brief. One worktree, one agent applies to redirects too.
21. **A merge's gates include every test that renders the touched component** (`look-yes-merge-needs-suite-of-touched-area-2026-10-12`): before any merge, including a trailing-review merge on the operator's yes, run `git grep -l <ComponentName> -- '*.test.*'` and those files, not a hand-picked directory. An unexplained failure in a lane's run is red until named.
22. **Agents may mark a reviewed draft PR ready** (ruling `2026-10-15-agents-may-undraft-reviewed-prs`): in MrJarrad repositories, once it has a passing gate run and a reviewer verdict with no red finding; where a session's safety check still refuses, un-drafting stays the operator's click. This supersedes "never the helper" in `release-deploy/references/RELEASE-PATH.md` for that case only.
   - **A draft PR is marked ready before the merge call**, because `merge_pull_request` returns 405 on a draft; the verdict is read with `pull_request_read get_comments` (or `get_reviews`), which is what satisfies `merge-review-gate.mjs`. DO: `update_pull_request draft:false`, read the verdict, then merge. DON'T: call merge on a draft, or count a verdict the session has not read.
   - **A wake-event turn that changed nothing is not a return** (DISC-294). A wake-event turn (a GitHub bot edit, a green check suite) is a return only when it made an edit, a push, a commit or a GitHub write, or says `next: parent`; `parent-return-stop.mjs` lets any other wake turn end with no chat text at all (the result goes to the Status doc). DO: end the turn when an event changes nothing. DON'T: send the parent "no change" per event while waiting on the operator.
23. **A yes opens a lane the same turn** (`2026-10-31-s43-parent-lessons`, DISC-221). When the operator says yes to a build row, the parent dispatches it that turn and writes the lane's branch or PR into the row's Notes. `session-resume.mjs` lists every open row carrying an operator yes and no lane id as "approved, not started". DO: dispatch, then add `lane claude/text-glow` to the row. DON'T: bank the yes and move on.
24. **The first status reply comes before housekeeping** (`2026-10-31-s44-parent-lessons`, DISC-224). A starting or resuming parent sends its first status reply from three reads only: `session-resume.mjs`, `needed-from-you.mjs` and the cockpit. Merges, the helper sweep, re-point messages and PR or session reads come after it, in a turn the parent starts itself with one `send_later` (`delay_minutes: 1`) armed before the reply. Measured by `node <plugin>/hooks/scripts/start-cost.mjs <transcript.jsonl> --max 40000`. DO: arm the follow-up, reply, then merge and sweep. DON'T: read PR files and session lists before the operator has a status.

## Parent practice

- **Compare refs without touching the working tree**, because a checkout over the tree overwrites committed work (`2026-11-10-s74-parent-lessons`). DO: compare against another ref in a throwaway `git worktree add`. DON'T: check another ref's files out over the working tree (`git checkout <ref> -- .`).
- **Reviewed branches stay still**: once a reviewer is dispatched on a PR, push nothing more to that branch until it merges; new notes go on their own branch, because the merge gate refuses a head past the reviewed one (`2026-11-10-s75-parent-lessons`). DON'T: push a note commit onto a branch a reviewer has a verdict on.
- **Figma contracts need Figma tools**: a brief that says "read the Figma live" goes only to a vehicle that has the Figma tools (a helper session); the parent checks the persona's tool list before choosing in-session, never an in-session reviewer (`2026-11-10-s75-parent-lessons`).
- **Load sheds heavy lanes**: at the first load warning the next heavy lane (suite, build, browser) goes to a helper session; reviewers that only read git stay in-session (`2026-11-10-s75-parent-lessons`).
- **Proof commands run plain**: run the proof command plain, exactly as the gate prints it, never piped through `cut`, `head` or `grep`; `merge-review-gate.mjs` counts only a plain run (`2026-11-10-s75-parent-lessons`).
- **Helpers never merge**: a helper brief ends at "PR open, review-ready" and never asks for a merge; the parent merges reviewed PRs itself, after `add_repo` with `access: "push"`, because a session message is not the operator's go (`2026-11-10-s77-parent-lessons`). DON'T: message a helper "now merge it".
- **Re-read the PR's comments after the last post, then merge**: `get_comments` again, then `merge_pull_request` with `expectedHeadSha`, because the gate reads the verdict from a read made after the final post (`2026-11-12-s83-parent-lessons`).
