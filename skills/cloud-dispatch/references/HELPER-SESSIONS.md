# Helper sessions — dispatching a helper cloud session end to end

A helper is a `create_session` child: a whole cloud session that does one lane while the parent keeps talking to the operator. The parent reads this once, top to bottom, when it sends a lane out (`cloud-dispatch` § Capacity before dispatch). The standing rules for helpers (the brief opener, the sweep cadence, answering a blocked helper, the archive trigger) are `routing` HARD-RULES 19 and are not restated here; this page is the steps around them.

## 1. Before creating it

- **Your own id.** `get_session` with no `session_id` returns this session's id; it goes in the brief.
- **Source repo.** `source_url` is the one repo the helper builds in (a product repo, or this plugin repo); it is cloned fresh at `source_revision` (default branch). The brief names the branch to create from it. Pass `blob_limit_kb` / `sparse_checkout_paths` only for a very large repo.
- **Other repos.** **The brief lists every repo the lane touches, each with its access level** (`read` or `push`) — `create_session` takes one `source_url`, so the rest are the helper's to attach (DISC-249: a helper that finds a repo mid-lane and calls `add_repo` is refused as a self-granted permission and the ask lands on the operator). **The auto-mode check refuses `add_repo` intermittently** (s72: two helpers stalled, a third attached two repos fine): a helper whose `add_repo` is refused stops and returns the refusal text verbatim as `next: parent`; the parent runs that lane as a local engineer in its own session. Never retry the same repo, never ask the operator. The helper attaches each with `add_repo` and then clones it itself: one clone at a time, a generous timeout (about 10 minutes), then `register_repo_root`. The vault is read-only unless the brief says otherwise, and a vault write gets its own worktree (output style, "Parent routes"). **A brief that lets the helper write the vault names the helper's own vault branch** (`claude/<lane>-progress`, its own draft PR), never the parent's (DISC-221, s43: a helper's MCP write truncated a file on the parent's branch). **That branch always bases on vault main**, never on another PR's branch (s44: merging vault #343 into the s43 notes branch moved #354's head after its review). **Preview builds are handed out serially**: the helper waits for the parent's "build now" and watches the PR's Workers comment on GitHub, never the Cloudflare API (`release-deploy` § Gate shape). Through the GitHub MCP, an update sends the file's whole content; `vault-mcp-write-guard.mjs` refuses an update under 256 bytes or under half the size the session last read.
- **Permission mode.** Pass `permission_mode: "auto"` on every helper (s61: after plan mode the parent was ask-first, so eight helpers inherited it and sat two hours on an approval nobody saw). A refusal means the parent is not in auto: say so at once. `hooks/bin/helper-create-gate.mjs` denies a `create_session` with no `permission_mode`. DO: `permission_mode: "auto"`, then the HARD-RULES 19 check. DON'T: omit it and inherit the mode.
- **Model.** Pass `model` explicitly. Pick it per `model-routing` (job shape × complexity), never by inheriting the parent's by accident.
- **Environment.** Omit `environment_id` to inherit the parent's.
- **Title and tags.** The title follows the session-titles ruling (`session-titles-2026-10-15`, in the output style). Tag the lane (`set_session_tags`, or `tags` on create), for example `helper` and the lane name.
- **Brief.** `dispatch-brief` shape, opening and closing as HARD-RULES 19 says. It names the contract, the branch, the gates, and where the return goes. It also says, in its first lines, that every read-back and the final return go to the parent with `send_message` using the parent id above, and that the helper's own transcript is not a channel to the parent. Ask for a read-back and a wait for "go" only when the lane needs one (a contested or system-size lane); the default is to start. **A brief kept as a vault file is merged to vault main before dispatch**, and the prompt points at main (s61: a helper that started from main could not find a brief left on the parent's branch). **A brief that cites a row the parent just added waits until the parent's notes PR merges** (s69: HT-84 lived only on the parent's notes branch and X3 could not start). **Never ask a helper to merge when its brief forbids merging** (s63: three helpers rightly refused); who merges is `routing` HARD-RULES 6. **Every reviewer brief says to post the verdict on the PR; never "do not post on the PR"** (form in `agents/reviewer.md` § Verdict shape): the merge gate reads PR comments, so a verdict sent only by message cannot clear a merge (s70: R-UP1).

## 2. What the helper does

1. Starts at once, and first writes the parent id to `~/.claude/helper-session` (the marker the Stop hook reads). On a brief that asks for a read-back, it sends the read-back to the parent with `send_message` (`session_id` = the parent id above) and stops until the parent's "go" arrives (`ReadNotifications`). A read-back written only in its transcript does not reach the parent. It then attaches every listed repo with `add_repo` as its first step, before any work. A repo the brief did not list is `next: parent`, never a question to the operator.
2. **Reports the plugin version it loaded** in its read-back or first return (the highest version directory under `~/.claude/plugins/cache/discipline/discipline/`, or `installed_plugins.json`; "not found" is an answer). A cloud container has loaded an older version than main before; this is how the parent learns it.
3. Builds on the branch the brief names. It pushes to that branch only, never main, and opens one draft PR. A review link it sends meets `present-for-review` § Before the link goes out: opened cold first, in the state to review.
4. **Posts its return on the PR** as a comment (PR link, head sha, the ledger the brief asked for, the suite tail) **and sends the same return to the parent with `send_message`**. The PR comment is the banked result; the message is what tells the parent it is ready. If a turn ends with a return and no `send_message`, the Stop hook `parent-return-stop.mjs` holds it once and asks for the send (a one-line ack under 200 characters with no `next: parent` is let through).
5. **A reviewer brief names the id to sign with** (s83: reviewers copied the parent's id from `~/.claude/helper-session` into `reviewer:`): "`reviewer: session_<the id your own get_session returns>`; `~/.claude/helper-session` holds the parent's id." `helper-create-gate.mjs` refuses a `Persona: reviewer` brief that never names `get_session`.
5a. **A reviewer helper sends its verdict block to the parent verbatim** (DISC-221, s43: three reviewer helpers were refused `add_repo … push`). The block keeps the heading `agents/reviewer.md` § Verdict defines and adds, under it, `reviewer: <its own session id>` (from `get_session`); the parent posts the block on the PR unchanged, and the merge gates read that line. The `reviewer:` line follows the `reviewer:` line rule in `agents/reviewer.md` § Verdict shape (your own `get_session` id, never the helper-session file). This is the default in every reviewer brief; the reviewer posts on the PR itself only when the brief says it has push.
5b. **A design-system review whose contract needs `handoff-css` installed (the golden test) is a cloud reviewer with `handoff-css` attached `read`, or a local one** (s84 → s85). s84: a cloud reviewer's `add_repo handoff-css` was refused ("Access Added As A Means"). s85, checked in a cloud session: `handoff-css` is public, so `add_repo … access: "read"` returns `read_available` (anonymous clone, no refusal; one session, s85, unconfirmed beyond), but a read attach carries no GitHub API tools, so the reviewer cannot post on a `handoff-css` PR (the design-system PR is a different repo and is unaffected). The brief lists `handoff-css` as `read`. A refused `add_repo`, or an install that 403s "GitHub access to this repository is not enabled for this session", is `next: parent` verbatim; the parent runs that review as a local in-session reviewer (it has `handoff-css` attached) with `Local because: (c)`. DO: list `handoff-css (read)` and send the verdict block to the parent. DON'T: retry `add_repo`, or ask the operator.
6. A Mac job it files from its branch goes in `queue/mac/review/`, never `pending/` (`MAC-JOBS.md`, DISC-233).

## 3. How the parent sweeps it

- **Backstop.** Arm one `send_later` about 50 minutes out per dispatch (HARD-RULES 19); delete it when the return arrives.
- `get_session` shows `status_bucket`: `working`, `blocked`, `review_ready`, `completed` or `failed` (`failed` means its last turn errored). Cadence and blocked helpers: HARD-RULES 19.
- To see what a helper is doing, read its progress file (the brief names it) first; otherwise `list_events` with `kinds: ["result"]` and `limit: 5`, widening to `"assistant"` only when that does not answer (DISC-224, s44: 12.7k chars for one read).
- Redirect a running helper with `send_message` on that one channel (HARD-RULES 20); never a second helper for the same lane.
- **Read the source before relaying a negative** (s63, s64, s65): before telling the operator a lane stalled or a gate went red, read its progress file or `get_session`, and the PR's comments (a "no suite tail" red once ignored the tail already on the PR). Each `## Build in Progress` bullet names when the helper last reported; past 30 minutes of silence, `get_session` and nudge before repeating "running". DO: "L1 — last report 12:11, nudged 12:45". DON'T: repeat "still running" for hours from memory.
- **A follow-up after a lane lands is a fresh helper, not a message to the old one** (s84 HT-128 docs: a helper read `~/.claude/helper-session` as its own id and refused a follow-up as unverified). s85: two helpers sent a new parent id by message accepted follow-up lanes, so a message to a live helper works only when it is a re-point that names the new parent id first (unconfirmed beyond those two; a refusal is the default expectation). DO: `create_session` for the follow-up, or re-point first and say so. DON'T: send a landed helper a new lane and wait.
- **Resend what may have crossed** (s64, s67): when a read-back or return does not reflect a "go" or a correction already sent, resend it verbatim in one line, with the decision it belongs to; never assume it landed.

## 4. Landing

Read the PR comment, bank the result, then `archive_session` as HARD-RULES 19 says. At wrap, archive any helper whose work has landed (`wrap` CLOSING-CHECKS 6). The helper sweep (HARD-RULES 19) catches any helper a parent missed, at the next session start or wrap. A helper with an open PR or an unanswered operator ask is not archived; the next parent adopts it (HARD-RULES 19, rules 1 and 2, DISC-291). The guard checks for open PRs by lookup, not by paging the helper's history (DISC-315): once the helper is idle, `get_session` it, then run exactly `gh api -X GET search/issues -f q='is:pr is:open <helper session id>'` and, for each branch `get_session` shows for it (a helper's are the values of `external_metadata.current_branches`), the same with `head:<branch>` in place of the id. No `repo:`, no other qualifier, no pipe, nothing else is read as a lookup. The id search finds PRs whose description links the session but can lag a fresh PR; the `head:` search does not. Any open PR returned refuses the archive; a failed or truncated lookup refuses it too. A subagent's lookups count (DISC-284). A subagent's lookup counts only when it is time-stamped at or after your last `get_session` of the helper. Known limits: the search reaches only repos this session's GitHub grant covers, so a helper's PR in any other repo is invisible to it; and a helper that is idle with no branch recorded (`current_branches` of `{"": null}`) whose PR is newer than the id search's lag (about 15 minutes) is not found by either lookup.

- **Archive from the session that created the helper, at its lane close, and try the call before saying it cannot be done** (s77): the auto-mode check allows `archive_session` on a helper this session created and refuses another parent's. DO: archive at the lane close, and on a refusal name it as one line. DON'T: tell the operator archiving is impossible after one refusal on an old helper (he corrected it: "you've been doing this in prior sessions").
